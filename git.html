Git et GitHub

Garder l'historique de ton code, revenir en arrière sans peur, travailler sur plusieurs machines et à plusieurs.

Niveau débutantDurée ~1 h 30 à 2 hPrérequis savoir ouvrir un terminal
Objectifs

À la fin de ce cours, tu sauras…

  1. Expliquer les zones de Git : dossier de travail, index, dépôt local, dépôt distant.
  2. Faire le cycle quotidien : status, add, commit, push, pull.
  3. Travailler sur deux ordinateurs sans perdre de travail.
  4. Créer des branches, les fusionner et résoudre un conflit.
  5. Choisir la bonne commande pour annuler quelque chose.
  6. Comprendre ce que GitHub ajoute, et ce que « public » veut vraiment dire.
Le principe

Git n'est pas GitHub

GIT

Le logiciel

Installé sur ta machine. Il enregistre des instantanés de ton projet (les commits) et fonctionne sans Internet.

GITHUB

Le service en ligne

Héberge une copie de ton dépôt. Il ajoute la sauvegarde, le partage, les pull requests, les issues… GitLab et Bitbucket font la même chose.

  • Historique : chaque version est gardée, avec qui l'a faite, quand et pourquoi.
  • Sécurité : tu peux tester sans risque, puis revenir à une version qui marchait.
  • Synchronisation : le même projet sur plusieurs ordinateurs ou entre plusieurs personnes.
Démarrer

Installer et configurer Git

# vérifier l'installation
git --version

# ton identité (apparaît dans chaque commit)
git config --global user.name "Prénom Nom"
git config --global user.email "toi@exemple.be"

# nommer la branche principale « main »
git config --global init.defaultBranch main

# Windows : gérer les fins de ligne
git config --global core.autocrlf true

# voir toute la configuration
git config --list
  • Sous Windows, installe Git for Windows : il fournit aussi Git Bash, un terminal pratique.
  • L'adresse e-mail doit correspondre à celle de ton compte GitHub pour que tes commits soient reliés à ton profil.
  • --global s'applique à tous tes projets. Sans lui, le réglage ne vaut que pour le dépôt courant.
  • VS Code intègre Git : onglet « Contrôle de code source ». Comprendre les commandes aide à savoir ce que font ses boutons.

Démarrer

Créer un dépôt et le relier à GitHub

Partir d'un projet existant

# dans le dossier du projet
git init
git add .
git commit -m "Premier commit"

# dépôt vide créé sur github.com
git remote add origin https://github.com/moi/projet.git
git push -u origin main

Partir d'un dépôt GitHub

git clone https://github.com/moi/projet.git
cd projet
  • origin est le nom habituel du dépôt distant. git remote -v l'affiche.
  • -u relie ta branche locale à la branche distante : ensuite, git push et git pull suffisent.
  • Crée le .gitignore avant le premier git add ..
Au quotidien

Le cycle de base

# où j'en suis ? (à taper souvent)
git status

# qu'est-ce que j'ai changé ?
git diff

# préparer puis enregistrer
git add src/page.tsx      # un fichier
git add .                 # tout
git commit -m "Ajoute le formulaire de contact"

# envoyer sur GitHub
git push

# voir l'historique
git log --oneline -10

Un bon commit

  • Petit : un seul changement logique (« corrige le menu mobile »), pas « plein de trucs ».
  • Message clair, à l'impératif : Ajoute, Corrige, Supprime…
  • Qui fonctionne : le projet doit encore démarrer après le commit.
  • Relis git diff avant chaque commit : c'est là que tu repères un fichier oublié ou un secret.
Comprendre

Ce qu'est vraiment un commit

a1b2c3dPremier commit
←
e4f5a6bAjoute le formulaire
←
c7d8e9fCorrige le menu · main · HEAD
  • Un commit est un instantané complet du projet, avec un auteur, une date, un message et un lien vers son parent.
  • Son identifiant (le hash, ex. c7d8e9f…) est calculé à partir de son contenu : modifier un commit change son hash.
  • Une branche n'est qu'une étiquette qui pointe vers un commit, et avance à chaque nouveau commit.
  • HEAD désigne l'endroit où tu te trouves : en général, la branche sur laquelle tu travailles.
Comprendre

Lire l'historique et les différences

# historique compact, avec les branches
git log --oneline --graph --all

# détail d'un commit
git show c7d8e9f

# ce qui a changé, pas encore ajouté
git diff

# ce qui est dans l'index (prochain commit)
git diff --staged

# différences entre deux branches
git diff main..nouvelle-navbar

# qui a modifié chaque ligne, et quand
git blame src/page.tsx
  • Dans git log, appuie sur q pour sortir, sur Espace pour descendre.
  • git diff --staged avant de commiter montre exactement ce qui va être enregistré.
  • Sur GitHub, l'onglet Commits et le bouton Blame d'un fichier donnent les mêmes informations en visuel.
  • On peut utiliser un hash raccourci (7 caractères) dans toutes les commandes.
Ce qu'on ne versionne pas

Le fichier .gitignore

# .gitignore
node_modules/
.next/
dist/

# secrets et config locale
.env
.env*.local

# fichiers système
.DS_Store
Thumbs.db
  • Les dépendances (node_modules) se réinstallent avec npm install : inutile de les stocker.
  • Les dossiers de build se régénèrent.
  • Les secrets (.env) ne doivent jamais entrer dans l'historique.
  • Crée le .gitignore dès le début : il n'agit que sur les fichiers pas encore suivis.

Fichier déjà suivi par erreur ? git rm --cached .env le retire du suivi sans le supprimer de ton disque. Il reste quand même dans les anciens commits.

Local et distant

fetch, pull, push

CommandeEffetQuand

origin/main est la dernière version connue de la branche main sur GitHub. Elle ne se met à jour qu'au fetch ou au pull : ce n'est pas du temps réel.

Local et distant

Les branches distantes

# publier une nouvelle branche
git push -u origin nouvelle-navbar

# voir toutes les branches, locales et distantes
git branch -a

# récupérer une branche créée par quelqu'un d'autre
git fetch
git switch sa-branche

# supprimer une branche distante
git push origin --delete nouvelle-navbar

# nettoyer les branches distantes disparues
git fetch --prune
  • Une branche créée en local n'existe pas sur GitHub tant que tu ne l'as pas poussée.
  • git switch sa-branche crée automatiquement la branche locale qui suit origin/sa-branche.
  • git status indique si tu es « en avance » (commits à pousser) ou « en retard » (commits à récupérer) sur la branche distante.
  • Supprimer une branche après sa fusion garde le dépôt lisible.
Plusieurs ordinateurs

La routine qui évite les ennuis

En arrivant sur une machine

  1. git status : rien en attente ?
  2. git pull : récupère ce que tu as fait ailleurs.
  3. Seulement ensuite, tu travailles.

Avant de quitter une machine

  1. git add . puis git commit.
  2. git push.
  3. Vérifie sur GitHub que le commit est bien là.

« push rejected (non-fast-forward) » : le distant contient des commits que tu n'as pas. Ne force pas : fais git pull, règle les éventuels conflits, puis git push.

Branches

Travailler en parallèle sans casser main

Une branche est une ligne de travail séparée. Techniquement, c'est juste un pointeur vers un commit, donc c'est léger et rapide.

# créer une branche et y aller
git switch -c nouvelle-navbar

# … commits …

# revenir et fusionner
git switch main
git merge nouvelle-navbar
git branch -d nouvelle-navbar

Pourquoi c'est utile

  • main reste toujours dans un état qui fonctionne (et déployable).
  • Tu peux abandonner une idée en supprimant la branche.
  • Sur GitHub, une branche permet d'ouvrir une pull request pour relire avant de fusionner.
  • Les hébergeurs créent souvent un déploiement de prévisualisation par branche.
Fusionner

Merge ou rebase ?

MERGE

Garde l'histoire telle quelle

Crée un commit de fusion qui réunit les deux branches. Aucun commit existant n'est modifié.

Si main n'a pas bougé entre-temps, Git avance simplement le pointeur : c'est un fast-forward.

REBASE

Réécrit pour une histoire linéaire

Rejoue tes commits par-dessus la dernière version de main. Plus propre à lire, mais les commits changent d'identifiant.

Ne rebase jamais des commits déjà poussés et partagés avec d'autres.

Pour débuter : utilise merge. C'est sûr et ça ne réécrit rien. Le rebase est un confort, pas une obligation.

Fusionner

Nettoyer ses commits avant de partager

# retravailler les 3 derniers commits
git rebase -i HEAD~3

# l'éditeur s'ouvre :
pick   a1b2c3d Ajoute le formulaire
squash e4f5a6b oups, faute de frappe
reword c7d8e9f Corrige le menu

# modifier seulement le dernier message
git commit --amend -m "Nouveau message"
  • pick : garder le commit ; reword : changer son message ; squash : le fusionner avec le précédent ; drop : le supprimer.
  • Utile pour transformer « wip », « oups », « ça marche ? » en commits propres avant une pull request.
  • Ça réécrit l'historique : uniquement sur des commits qui n'ont pas encore été partagés.
  • En cas de doute : git rebase --abort annule tout.
Conflits

Résoudre un conflit sans paniquer

// Git a marqué le fichier :
<<<<<<< HEAD
  <h1>Bienvenue</h1>
=======
  <h1>Bonjour à tous</h1>
>>>>>>> nouvelle-navbar
  1. Un conflit arrive quand les deux côtés ont modifié les mêmes lignes. Ce n'est pas une erreur grave.
  2. Au-dessus de ======= : ta version (HEAD). En dessous : celle qui arrive.
  3. Édite pour garder le bon résultat, et supprime les trois marqueurs.
  4. git add fichier puis git commit pour terminer.
  5. Perdu ? git merge --abort revient à l'état d'avant.

VS Code affiche des boutons « Accept Current / Incoming / Both » au-dessus de chaque conflit.

Conflits

Moins de conflits au quotidien

  • Pull souvent : plus tu attends, plus les deux versions divergent.
  • Des branches courtes : fusionner après quelques jours plutôt que quelques semaines.
  • Des commits petits et ciblés.
  • Un formateur automatique (Prettier) partagé par tous : il évite les conflits de mise en forme.

Le cas de package-lock.json

Fichier généré, souvent en conflit. Plutôt que de le résoudre à la main :

git checkout --theirs package-lock.json
npm install
git add package-lock.json

On repart de la version qui arrive, puis npm install le régénère proprement avec tes dépendances.

Mettre de côté

git stash : la poche temporaire

# mettre de côté les modifs en cours
git stash

# faire autre chose, par exemple :
git pull

# récupérer les modifs
git stash pop

# voir ce qui est en poche
git stash list
  • Utile quand git pull ou git switch refuse parce que tu as des modifications non commitées.
  • stash pop réapplique puis vide la poche. stash apply réapplique en gardant la copie.
  • Les nouveaux fichiers ne sont pas inclus par défaut : ajoute -u.
  • Ne laisse pas traîner des stashs pendant des semaines : un commit sur une branche est plus clair.
Outils utiles

Récupérer un seul commit : cherry-pick

# trouver le commit voulu
git log --oneline autre-branche

# le copier sur la branche courante
git switch main
git cherry-pick e4f5a6b

# en cas de conflit : résoudre puis
git cherry-pick --continue
# ou abandonner
git cherry-pick --abort
  • cherry-pick recopie les changements d'un commit précis sur ta branche actuelle, avec un nouveau hash.
  • Cas typique : une correction urgente faite sur une branche de travail, dont tu as besoin tout de suite sur main.
  • À utiliser ponctuellement : pour tout récupérer, une fusion reste plus claire.
Annuler

Quelle commande pour revenir en arrière ?

Je veux…CommandeRisque
Annuler mes modifs d'un fichiergit restore fichierModifs perdues
Retirer un fichier de l'indexgit restore --staged fichierAucun
Corriger le dernier commit (non poussé)git commit --amendRéécrit le commit
Annuler un commit déjà pousségit revert <hash>Aucun : crée un commit inverse
Revenir à la version de GitHubgit fetch puis git reset --hard origin/mainTout le non-poussé est perdu

Filet de sécurité : git reflog liste tous les endroits où tu es passé, même après un reset. Un commit « perdu » se retrouve presque toujours là.

Annuler

Retrouver un travail « perdu »

$ git reflog
c7d8e9f HEAD@{0}: reset: moving to origin/main
9a8b7c6 HEAD@{1}: commit: Ajoute la page contact
e4f5a6b HEAD@{2}: commit: Ajoute le formulaire

# créer une branche sur le commit perdu
git branch sauvetage 9a8b7c6

# ou y revenir directement
git reset --hard 9a8b7c6
  • Le reflog note chaque déplacement de HEAD pendant environ 90 jours, même après un reset --hard ou un rebase raté.
  • Repère la ligne juste avant l'erreur et récupère son hash.
  • Créer une branche dessus est le plus sûr : tu ne touches à rien d'autre.
  • Limite : des modifications jamais commitées ne sont pas dans le reflog. Commite souvent.
Ce qui est public

L'historique n'oublie rien

  • Supprimer un fichier dans un nouveau commit ne l'efface pas des commits précédents.
  • Un dépôt public montre tout : le code, toutes les branches, tout l'historique.
  • Il n'existe pas de dépôt « public sauf certains fichiers ».

Une clé a été poussée ?

  1. Régénère la clé tout de suite chez le fournisseur : c'est la seule vraie protection.
  2. Retire le fichier du suivi et ajoute-le au .gitignore.
  3. Si nécessaire, réécris l'historique (git filter-repo), en sachant que des copies ont pu être faites.

Pour montrer un projet sans montrer le code : dépôt privé pour le code, et dépôt public avec un README, des captures et un lien vers la démo.

GitHub

Se connecter à GitHub en SSH

# 1. créer une paire de clés
ssh-keygen -t ed25519 -C "toi@exemple.be"

# 2. afficher la clé PUBLIQUE à copier
cat ~/.ssh/id_ed25519.pub

# 3. la coller dans GitHub :
#    Settings → SSH and GPG keys → New SSH key

# 4. tester
ssh -T git@github.com

# 5. utiliser l'adresse SSH du dépôt
git remote set-url origin git@github.com:moi/projet.git
  • GitHub n'accepte plus le mot de passe du compte dans le terminal : il faut une clé SSH, un jeton ou GitHub CLI (gh auth login).
  • La clé privée (sans .pub) ne quitte jamais ton ordinateur.
  • Une clé par ordinateur : si tu en perds un, tu supprimes seulement sa clé dans GitHub.
GitHub

Ce que GitHub ajoute à Git

PULL REQUEST

Relire avant de fusionner

Propose de fusionner une branche, avec la liste des changements, des commentaires et des vérifications automatiques.

ISSUES

Suivre le travail

Bugs, idées, tâches. Un commit qui contient « fixes #12 » ferme automatiquement l'issue 12 à la fusion.

ORGANISATIONS

Travailler à plusieurs

Un compte partagé qui possède les dépôts, avec des équipes et des droits (lecture, écriture, admin).

  • Le README.md est la vitrine du dépôt : à quoi sert le projet, comment l'installer, comment le lancer.
  • Pour s'authentifier depuis le terminal : clé SSH ou GitHub CLI (gh auth login), plus de mot de passe.
GitHub

Le cycle d'une pull request

  1. Branche : git switch -c ajout-recherche, puis commits.
  2. Push : git push -u origin ajout-recherche. GitHub propose d'ouvrir une pull request.
  3. Description : ce qui change, pourquoi, comment tester, captures si c'est visuel.
  4. Vérifications : tests automatiques, déploiement de prévisualisation, relecture.
  5. Corrections : de nouveaux commits sur la même branche mettent la PR à jour.
  6. Fusion sur main (merge, squash ou rebase), puis suppression de la branche.

Même seul sur un projet, passer par des PR donne un historique clair et une étape de relecture avant la production.

GitHub

Tags, versions et releases

v2.4.1
2 · majeurChangement qui casse la compatibilité
4 · mineurNouvelle fonctionnalité compatible
1 · correctifCorrection de bug

C'est le versionnement sémantique (semver), utilisé par npm et la plupart des projets.

# marquer une version
git tag -a v1.0.0 -m "Première version"
git push origin v1.0.0

# lister les versions
git tag
  • Un tag est une étiquette fixe sur un commit, contrairement à une branche.
  • Sur GitHub, une release ajoute à un tag des notes de version et des fichiers à télécharger.
GitHub

Automatiser avec GitHub Actions

# .github/workflows/verifs.yml
name: Vérifications
on: [push, pull_request]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npm run lint
      - run: npm run build
  • Un workflow est un fichier YAML dans .github/workflows/. Il s'exécute sur les serveurs de GitHub à chaque événement choisi (push, pull_request, horaire…).
  • Ici : à chaque push, GitHub installe les dépendances, vérifie le code et tente un build. Une croix rouge apparaît sur le commit en cas d'échec.
  • Les secrets (clés d'API) se déclarent dans Settings → Secrets and variables, jamais dans le fichier.
  • Gratuit dans une large limite pour les dépôts publics.
GitHub

Publier un site avec GitHub Pages

  1. Mets des fichiers HTML, CSS et JS dans un dépôt (un index.html à la racine).
  2. Settings → Pages → Deploy from a branch → main et / (root).
  3. Une minute plus tard : https://utilisateur.github.io/depot/.
  4. Chaque push redéploie automatiquement.

Bon à savoir

  • Uniquement des fichiers statiques : pas de serveur, pas de base de données.
  • Gratuit pour les dépôts publics.
  • Un fichier vide .nojekyll désactive le traitement Jekyll et publie les fichiers tels quels.
  • Un nom de domaine personnalisé se configure dans la même page, avec un CNAME dans ta zone DNS.

À retenir

L'essentiel en 6 phrases

  • Git = l'historique, GitHub = la copie en ligne.
  • add prépare, commit enregistre, push envoie.
  • Pull en arrivant, push en partant.
  • Une branche par nouvelle fonctionnalité, main toujours stable.
  • revert pour ce qui est poussé, reset seulement en local.
  • Ce qui a été commité reste dans l'historique.
Exercices

Teste-toi

Différence entre git fetch et git pull ?

fetch télécharge les nouveautés sans toucher à tes fichiers. pull fait un fetch puis intègre les changements dans ta branche.

Ton git push est refusé (« non-fast-forward »). Que faire ?

Le distant a des commits que tu n'as pas. Fais git pull, résous les conflits éventuels, puis repousse. Évite --force.

Tu as poussé un commit qui casse le site. Comment l'annuler proprement ?

git revert <hash> crée un nouveau commit qui annule le précédent, sans réécrire l'historique partagé.

Tu veux jeter tout ton travail local et revenir exactement à la version GitHub.

git fetch puis git reset --hard origin/main. Attention : tout ce qui n'est pas poussé est perdu (sauf via git reflog pour les commits).

Ton .env apparaît sur GitHub alors qu'il est dans .gitignore. Pourquoi ?

Il était déjà suivi avant l'ajout au .gitignore. Fais git rm --cached .env, commite, et régénère les secrets qu'il contenait.

Exercices

Teste-toi (suite)

Tu as créé une branche en local, mais tes collègues ne la voient pas sur GitHub. Pourquoi ?

Elle n'a pas été poussée : git push -u origin nom-de-la-branche.

Comment voir exactement ce qui partira dans ton prochain commit ?

git diff --staged.

Tu as fait git reset --hard et perdu un commit. Comment le retrouver ?

git reflog pour trouver son hash, puis git branch sauvetage <hash>.

Ton prochain changement ajoute une fonctionnalité compatible à la v1.3.2. Nouvelle version ?

v1.4.0 : on incrémente le numéro mineur et on remet le correctif à zéro.

« Permission denied (publickey) » au moment du push. Que faire ?

Créer une clé SSH, ajouter la clé publique dans GitHub, tester avec ssh -T git@github.com, ou utiliser gh auth login.
