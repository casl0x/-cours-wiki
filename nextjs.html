Next.js
(App Router)

Comprendre comment Next.js organise une application : les routes, le rendu côté serveur ou client, la récupération de données et les API.

Niveau débutant → intermédiaireDurée ~1 hPrérequis bases de React et JavaScript
Objectifs

À la fin de ce cours, tu sauras…

  1. Créer des pages et des routes dynamiques à partir de l'arborescence de fichiers.
  2. Choisir entre Server Component et Client Component, et placer la frontière.
  3. Récupérer des données côté serveur et maîtriser le cache.
  4. Écrire une route API (Route Handler) et une Server Action.
  5. Protéger tes secrets avec les variables d'environnement.
  6. Savoir, pour chaque besoin, où mettre le code.
Le principe

Next.js = React + tout ce qui manque autour

React sait afficher des composants. Next.js ajoute ce qu'il faut pour en faire un site complet.

ROUTING

Par fichiers

Un dossier = un segment d'URL. Pas de configuration de routes à écrire.

RENDU

Serveur d'abord

Les pages sont générées sur le serveur : plus rapides à afficher, mieux référencées.

BACK-END

Intégré

Routes API et Server Actions dans le même projet, sans serveur séparé.

Ce cours porte sur l'App Router (dossier app/), le modèle actuel. L'ancien Pages Router (dossier pages/) fonctionne autrement : ne mélange pas les tutos des deux.

Routing

Un dossier = un segment d'URL

app/
├─ layout.tsx          ← cadre commun
├─ page.tsx            → /
├─ about/
│  └─ page.tsx         → /about
├─ blog/
│  ├─ page.tsx         → /blog
│  └─ [slug]/
│     └─ page.tsx      → /blog/mon-article
├─ (marketing)/        ← groupe, pas dans l'URL
│  └─ tarifs/page.tsx  → /tarifs
└─ api/
   └─ hello/route.ts   → /api/hello
  • Un dossier n'est une page publique que s'il contient un page.tsx.
  • [slug] : segment dynamique, sa valeur arrive dans params.
  • [...slug] : attrape plusieurs segments (/docs/a/b/c).
  • (groupe) : organise les fichiers ou partage un layout, sans changer l'URL.
  • _dossier : privé, jamais routé (pratique pour les composants).
Fichiers spéciaux

Les noms de fichiers ont un sens

FichierRôle
page.tsxLe contenu de la route. Sans lui, pas de page.
layout.tsxCadre partagé (navbar, footer). Persiste entre les navigations. Le layout racine contient <html> et <body>.
loading.tsxAffiché instantanément pendant que la page charge ses données.
error.tsxRemplace la page si une erreur survient. Doit être un Client Component.
not-found.tsxPage 404, aussi déclenchée par notFound().
route.tsPoint d'API (GET, POST…). Ne peut pas coexister avec page.tsx dans le même dossier.
Routes dynamiques

Lire les paramètres de l'URL

// app/blog/[slug]/page.tsx
type Props = {
  params: Promise<{ slug: string }>;
  searchParams: Promise<{ page?: string }>;
};

export default async function Page(
  { params, searchParams }: Props
) {
  const { slug } = await params;
  const { page = "1" } = await searchParams;

  return <h1>Article {slug}, page {page}</h1>;
}
  • /blog/hello?page=2 donne slug = "hello" et page = "2".
  • Depuis Next.js 15, params et searchParams sont des promesses : il faut les await.
  • Les valeurs sont toujours des chaînes. Convertis-les : Number(id).

Dans un Client Component, on lit les paramètres avec les hooks useParams() et useSearchParams().

Le concept central

Server Components vs Client Components

Server Component (par défaut)Client Component ("use client")
S'exécuteSur le serveur uniquementRendu sur le serveur, puis « hydraté » dans le navigateur
PeutÊtre async, lire une base de données, utiliser des secretsUtiliser useState, useEffect, onClick, window, localStorage
Ne peut pasUtiliser des hooks ni des événementsAccéder aux secrets ni à la base directement
JavaScript envoyéAucunLe code du composant et ses dépendances
À utiliser pourAfficher des données, la mise en pageBoutons, formulaires interactifs, animations

Règle : tout est Server Component par défaut. Ajoute "use client" seulement là où il faut de l'interactivité.

La frontière

Pousser "use client" le plus bas possible

// app/produit/page.tsx  (Server)
import LikeButton from "./LikeButton";

export default async function Page() {
  const p = await getProduit();   // côté serveur
  return (
    <article>
      <h1>{p.nom}</h1>
      <p>{p.description}</p>
      <LikeButton initial={p.likes} />
    </article>
  );
}
// app/produit/LikeButton.tsx
"use client";
import { useState } from "react";

export default function LikeButton(
  { initial }: { initial: number }
) {
  const [n, setN] = useState(initial);
  return (
    <button onClick={() => setN(n + 1)}>
      ♥ {n}
    </button>
  );
}

La page reste côté serveur ; seul le bouton est envoyé au navigateur. Les props passées d'un Server à un Client Component doivent être sérialisables (texte, nombres, objets simples… pas de fonctions).

Données

Récupérer des données côté serveur

// app/films/page.tsx
async function getFilms() {
  const res = await fetch(
    `${process.env.API_URL}/films`,
    { headers: { Authorization:
        `Bearer ${process.env.API_KEY}` } }
  );
  if (!res.ok) throw new Error("API indisponible");
  return res.json();
}

export default async function Page() {
  const films = await getFilms();
  return <ul>{films.map(f =>
    <li key={f.id}>{f.titre}</li>)}</ul>;
}
  • Le composant est async : on await directement, sans useEffect ni état de chargement manuel.
  • La clé d'API reste sur le serveur, jamais envoyée au navigateur.
  • Toujours vérifier res.ok : fetch ne lève pas d'erreur sur un 404 ou un 500.
  • Une erreur levée affiche error.tsx ; pendant l'attente, loading.tsx.
  • Plusieurs requêtes indépendantes ? Lance-les en parallèle avec Promise.all.
Cache

Choisir la fraîcheur des données

BesoinOption de fetch
Toujours à jour{ cache: "no-store" } (comportement par défaut depuis Next.js 15)
Données qui ne changent pas{ cache: "force-cache" }
Rafraîchir de temps en temps{ next: { revalidate: 3600 } } : au plus une fois par heure
Rafraîchir après une action{ next: { tags: ["films"] } } puis revalidateTag("films")

Les règles de cache ont changé entre les versions (14 → 15 → 16, avec la directive "use cache"). Avant de suivre un tutoriel, vérifie sa version et la doc officielle de la tienne : c'est la source n°1 de « pourquoi mes données ne se mettent pas à jour ? ».

Données côté client

Quand le navigateur doit charger lui-même

"use client";
import useSWR from "swr";

const fetcher = (url: string) =>
  fetch(url).then(r => r.json());

export default function Recherche(
  { q }: { q: string }
) {
  const { data, error, isLoading } =
    useSWR(`/api/search?q=${q}`, fetcher);

  if (isLoading) return <p>Chargement…</p>;
  if (error) return <p>Erreur</p>;
  return <Resultats items={data} />;
}

Cas typiques : une recherche qui suit la frappe, des données qui changent toutes les secondes, du contenu propre à l'utilisateur après une interaction.

  • Préfère une bibliothèque (SWR, TanStack Query) à useEffect + fetch : cache, nouvel essai et déduplication inclus.
  • Le client appelle ta route API, qui elle appelle le service externe avec la clé secrète.
Back-end intégré

Route Handlers : tes propres API

// app/api/films/route.ts
import { NextRequest } from "next/server";

export async function GET(req: NextRequest) {
  const q = req.nextUrl.searchParams.get("q");
  const films = await chercherFilms(q);
  return Response.json(films);
}

export async function POST(req: Request) {
  const body = await req.json();
  if (!body.titre)
    return Response.json(
      { erreur: "titre requis" }, { status: 400 });
  const film = await creerFilm(body);
  return Response.json(film, { status: 201 });
}
  • Une fonction exportée par méthode HTTP : GET, POST, PUT, PATCH, DELETE.
  • Utiles pour : un client JavaScript, une app mobile, un webhook, un service externe qui t'appelle.
  • Renvoie les bons codes : 200 OK, 201 créé, 400 requête invalide, 401 non connecté, 404 introuvable.
  • Valide toujours ce qui arrive (par exemple avec Zod) : tout le monde peut appeler l'URL.
Mutations

Server Actions : un formulaire sans API

// app/contact/actions.ts
"use server";
import { revalidatePath } from "next/cache";

export async function envoyer(formData: FormData) {
  const email = String(formData.get("email"));
  // vérifier, puis enregistrer en base…
  revalidatePath("/messages");
}

// app/contact/page.tsx
import { envoyer } from "./actions";
export default function Page() {
  return (
    <form action={envoyer}>
      <input name="email" type="email" />
      <button>Envoyer</button>
    </form>
  );
}
  • Une fonction marquée "use server" s'exécute sur le serveur, même appelée depuis un formulaire.
  • Next.js crée l'appel réseau pour toi : pas de route ni de fetch à écrire.
  • Fonctionne même avant le chargement du JavaScript.
  • C'est un point d'entrée public : vérifie l'utilisateur et les données dans l'action.
  • Côté client, useActionState donne le résultat et l'état « en cours ».
Configuration

Variables d'environnement et secrets

# .env.local  (jamais commité)
DATABASE_URL=postgres://…
API_KEY=sk_live_…

# visible dans le navigateur !
NEXT_PUBLIC_SITE_URL=https://exemple.be
  • Sans préfixe : accessible uniquement côté serveur. C'est là que vont les secrets.
  • NEXT_PUBLIC_ : copié dans le JavaScript envoyé au navigateur. Donc jamais de secret.
  • .env.local doit être dans .gitignore. Fournis un .env.example sans valeurs.
  • En production, déclare les mêmes variables chez l'hébergeur, puis redéploie (les NEXT_PUBLIC_ sont figées au build).

Une clé déjà poussée sur GitHub reste dans l'historique : considère-la comme compromise et régénère-la.

À retenir

L'essentiel en 6 phrases

  • Un dossier dans app/ = une route, s'il a un page.tsx.
  • Tout est Server Component par défaut.
  • "use client" uniquement pour l'interactivité, le plus bas possible.
  • On récupère les données en await-ant directement dans la page.
  • Formulaire → Server Action ; appel externe → Route Handler.
  • Secrets côté serveur, jamais en NEXT_PUBLIC_.
Exercices

Teste-toi

Quelle URL affiche app/(shop)/produits/[id]/page.tsx ?

/produits/123 (avec n'importe quelle valeur d'id). Le groupe (shop) n'apparaît pas dans l'URL.

Erreur « useState only works in Client Components ». Que faire ?

Ajouter "use client" en haut du fichier, ou mieux : extraire la partie interactive dans un petit composant client et laisser la page côté serveur.

Pourquoi la clé NEXT_PUBLIC_API_KEY est-elle une mauvaise idée ?

Le préfixe NEXT_PUBLIC_ l'inclut dans le JavaScript envoyé au navigateur : n'importe qui peut la lire.

Mes données ne se mettent pas à jour après une modification. Pistes ?

Vérifier les options de cache du fetch selon ta version, et appeler revalidatePath ou revalidateTag après la modification.

Un formulaire « s'inscrire à la newsletter » : Route Handler ou Server Action ?

Server Action : le formulaire est sur ton site et n'a pas besoin d'API publique. Le Route Handler sert si un client externe doit appeler l'URL.
